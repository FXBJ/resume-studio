## 一、调研结论

### 1.1 直接对标的开源 Skill（7 个）

| 项目 | 核心做法 | 亮点 | 可规避的弊端 |
|---|---|---|---|
| **vibe-resume-skill** | `raw.data.yaml` → 按 JD 导出 `resume.data.yaml` → 套 12 套官方模板 → 一页 HTML/PDF | 数据与版式彻底分离；「AI 必须套官方模板，不能自己发明版式」写成硬约束；密度自适应；换岗位只复制不删除 | **CC BY-NC 4.0 非商业许可**，不能商用；模板按设计风格分（实用系/个性系），用户仍要猜「投互联网用哪套」；改颜色字号靠自然语言，不参数化 |
| **cn-resume-optimizer** | 第 0 轮定向 → 逐题访谈 → 每轮落盘 `working_resume.md` → 合成 → 40 项自检 → 5 维百分制评分 | **断线可续**（每轮落盘）；CJK 安全 PDF 自带字体查找链；评分模型完整 | 依赖三件套 `fpdf2/fonttools/pdfplumber`，被依赖拖累；三套 style 仅 professional/modern/minimal；单问题流访谈易疲劳；无模板预览 |
| **ASu-skills** | 9 个入口：great-resume / make-resume / job-match / job-apply / interview / offer | 生态最全，简历到投递到 offer 跟踪闭环；`skills.registry.json` 单一事实源 | 过重（9 入口）；偏开发者群体；无行业模板维度 |
| **resume-generator** | 三阶段：收集 → 润色 → ChatGPT 生图做视觉 mockup → 用户选 → 转 Word | **预览优先**；fact sheet 机制（mockup 不得出现事实表外信息）；ATS/学术/中英双语 | 用图像生成做 mockup，事实保真度有风险，须显式区分「AI 风格图」与「文本准确预览」；产出 Word 而非网页 |
| **resume-matcher-skill** | HRBP 五步审计 + JD 逐条比对 + 重写 + 内置中文简历编辑器 | 招聘方视角审计；证据矩阵 | 只挑刺不做排版；编辑器与 Skill 分离，链路断 |
| **tech-resume** | 一次性访谈建 career profile，之后每个 JD 只问几个问题 → DOCX/PDF | profile/ 与 applications/ 分离；ATS 解析友好细则（单栏、无表格文本框、嵌入字体、无连字）；**反 AI 味 lint** | 只面向 tech 岗；DOCX 为主；无模板选择 |
| **ResumeWritingSkill** | 结构化数据或自由输入 → ATS 优化简历/CV/求职信 | power_verbs 动词库；ats_guide 关键词指南 | 无排版能力；纯文本产出 |

参照产品：**Reactive Resume**（12+ 模板、自定义 CSS、自托管）——自定义 CSS 门槛过高，非 Skill 形态。

### 1.2 共性弊端 → 本项目对策

| # | 弊端（真实痛点） | 本项目对策 |
|---|---|---|
| 1 | **编造数字/公司/职位**。7 个项目里 5 个把 "never invent" 写进 README，说明这是头号事故 | `check_facts.py` 把「嘱咐」变成**可执行闸门**：输出中每个数字必须能在 fact_sheet 找到来源，找不到就标红并不允许交付；缺数写 `【待补】`，绝不填一个看起来合理的值 |
| 2 | **AI 味重**。HR 三秒闻出套话 | `lint.py` 反 AI 味检查：套话词表、破折号、bullet 长度变异系数、`-ing` 结尾、空洞形容词、强动词覆盖率、证据密度 |
| 3 | **模板按设计风格分，不按行业分**，用户不会选 | 六套模板**按行业大类**分，选择成本为零：「你投什么行业」→ 直接定 |
| 4 | **改版要写代码**（Reactive Resume 要写 CSS；vibe 靠自然语言但不参数化） | `theme_overrides` 白名单参数化：12 个字段，自然语言 → 参数有明确映射表 |
| 5 | **一页靠缩字号硬塞** | 明确规则：超一页**先删与技能栏重复的枚举 bullet**，再砍低优先级模块，`font_scale` 每次只降 0.02；低于 0.85 时提醒先删内容 |
| 6 | **中断不可续** | 引导模式每轮落盘 `working.json`，断线可续 |
| 7 | **ATS 不友好**（表格、文本框、多栏、图片文字） | 渲染器**写死**单栏、无表格、无文本框、纯文字流、A4 `@page` 规则；`lint.py` 对 HTML 特征做 ERROR 级检查 |
| 8 | **中文场景坑**（CJK 字体、PDF 乱码） | 字体栈 `PingFang SC / STHeiti / Noto Sans CJK SC / Microsoft YaHei`；PDF 走浏览器打印，**零依赖**，从根上避开字体打包问题 |
| 9 | **许可限制**（vibe 为 CC BY-NC 4.0） | 采用 **MIT**，可自由商用与二次分发 |
| 10 | **面试闭环缺失** | `score.py` 提供 JD 匹配度与差距清单，投递前可自检 |

## 二、架构设计

### 2.1 三层数据分离（架构核心）

```
raw.json          事实清单——只增不删，一次录入终身复用
   │  按 JD 挑选 / 排序 / 侧重（复制，不删除）
   ▼
resume.json       本次投递版本——套模板直接渲染
   │
   ▼
theme             视觉参数——六套行业主题 + 用户白名单覆盖
```

关键规则：**投 B 岗位时从 raw 复制出新的 resume.json，绝不在 raw 上删改。**
raw 是资产，resume 是快照。这条规则直接解决了「同一段经历投多个岗位」的场景，
也是 vibe-resume-skill 被验证有效的核心设计。

### 2.2 一套骨架驱动六套模板

所有模板共用同一份单栏 ATS 友好 HTML 骨架，差异全部由主题变量驱动：

```
配色 accent / accent_soft / ink / muted / rule
字号 font_scale（相对 10.5pt 基准）
密度 density = compact | normal | relaxed
顺序 module_order（直接决定信息优先级）
栏题 section_style = bar | underline | plain | numbered
头像 show_photo / photo_w / photo_h / photo_radius
措辞 bullet_hint
```

**为什么这样设计**：六份独立模板意味着六份要维护的代码，改一个 bug 要改六处。
一套骨架 + 六个 dict，新增行业只需加一个 dict，且永远不会出现「某套模板排版崩了」的局部故障。

### 2.3 零依赖的技术选择

| 能力 | 常规做法 | 本项目做法 | 理由 |
|---|---|---|---|
| 数据格式 | PyYAML | **JSON** | YAML 需第三方库；JSON 标准库直接支持且无歧义 |
| 模板引擎 | Jinja2 | **Python 字符串 + 极简行内标记** | 模板极简，引入引擎不划算 |
| docx 解析 | python-docx | **`zipfile` + 正则抽 `word/document.xml`** | docx 本质是 zip，标准库可解 |
| PDF 导出 | fpdf2 / pdfkit / wkhtmltopdf | **浏览器打印 → 存为 PDF** | 从根上避开 CJK 字体打包、依赖安装、版本兼容三件事 |
| 中文分词 | jieba | **精选词库 + 边界字 + 子串去重** | 见 §5 迭代建议 |

## 三、双模式交互设计

### 3.1 引导模式（需求不明确的用户）

核心原则：**先定位，后收集；先盘点，后深挖**。顺序反了会大量返工——
没定位就收集，等于把超市搬回家再决定做什么菜。

| 步骤 | 轮次 | 做什么 |
|---|---|---|
| 1 定位 | 1—2 | 目标岗位 / 行业 / 城市 / 应届或社招 → 直接定主题与模块顺序 |
| 2 盘点 | 1 | 勾选式列出九类资产，**只问有没有，不问细节** → 建 raw 骨架 |
| 3 深挖 | 每段 3—5 | 按与岗位相关度排序，逐段用 **STAR-L** 挖（情境/任务/动作/结果/学习） |
| 4 差距 | 1 | 跑 lint + check_facts，把问题清单浓缩成人话 |
| 5 合成 | 0（模型主导） | 生成 resume.json → 质检 → 渲染 → 自读 |
| 6 交付 | — | HTML + PDF 方式 + 【待补】清单 + 模板选择理由 |

通用规则：一次只问一个问题；每轮落盘可续；用户说「跳过」立刻跳；
每 3 轮播报完成度；用户疲惫时主动收尾。

### 3.2 优化模式（已有清晰简历）

| 步骤 | 做什么 |
|---|---|
| 1 解析 | `parse_resume.py` 统一抽成纯文本 + 粗分段；PDF 读不出就让用户粘贴，不折腾依赖 |
| 2 建 fact_sheet | **最关键一步**——把原文全部事实抽成清单，后续只能引用清单内内容 |
| 3 结构化重组 | 按主题重排模块；修经历错位、日期格式不统一、职责型 bullet 等常见问题 |
| 4 润色 | 只改语序/句式/动词/拆分合并/详略，不改事实；给 before / after 让用户确认 |
| 5 质检交付 | lint + check_facts + render 三过才交付 |

## 四、测试记录

### 4.1 正向测试

| 测试 | 结果 |
|---|---|
| 六套主题渲染 | 全部成功，accent 各不相同 |
| HTML 结构 | DOCTYPE / 单栏无表格 / 无 textarea / 纯文字无图片 / A4 `@page` / 模块齐全 —— 全 PASS |
| 好样例 lint | `bullets=7 no_number_ratio=0.143 strong_verb_ratio=0.857 errors=0 warnings=0` |
| 好样例 check_facts | `unsourced=0`，`--strict` 退出码 0 |
| md 解析分段 | 各段正确识别 |
| docx 解析 | `zipfile` 方案成功，段落换行保留 |
| JD 评分（前端岗） | 84/100，覆盖率 79%，缺项精准 |
| JD 评分（产品岗） | 45/100 正确判为不匹配，差距清单干净 |
| 头像三场景 | 无图 / 坏路径 / 真实图分别输出对应 NOTE，真实图正确转 base64 内嵌 |

### 4.2 反向测试（验证质检真能抓出问题）

| 检查项 | 捕获结果 |
|---|---|
| AI 套话 | 命中「深耕」「赋能」「链路」及简介里的「良好的沟通能力」等 8 处 |
| 空洞形容词 | 「良好」无数字支撑 |
| 证据密度 | 3/5 条 bullet 无数字（60%） |
| 无源数字 | 精准抓出 `3%`、`47%`、`9800`、`128` 四个编造指标，`--strict` 退出码 1 |
| 参数越界 | `font_scale=9.9` 被拒：「需在 0.7—1.6 之间」 |
| 白名单外字段 | `bogus_field` 被静默忽略，不导致版式崩坏 |

### 4.3 页数实测方法论

页数是简历的硬指标，但**不能靠估**。可靠做法：

```bash
# 无头 Chrome 打印成 PDF，数 /Type /Page 得页数
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless --disable-gpu \
  --no-sandbox --no-pdf-header-footer --print-to-pdf=out.pdf "file://$PWD/resume.html"
python3 -c "import re;d=open('out.pdf','rb').read();print(len(re.findall(rb'/Type\s*/Page[^s]',d)))"
```

判断「还差多少进一页」：给 HTML 追加 `@page{size:210mm Xmm}`，二分 X 找到能成一页的最小值，
即为内容真实高度。

> 实测结论：`--dump-dom` + JS 探针测高度**不可用**（不执行脚本或时机太早）。
> 打印态 `.page{padding:0}` 会生效，所以减 padding 救不了页数，只能减内容。

**压页顺序**：① 删与「专业技能」栏重复的技能枚举 bullet ② 砍 `volunteer` / `campus`
③ `font_scale` 每次降 0.02 ④ 仍不行才接受两页。低于 0.85 必须先删内容。

## 六、与创作大赛类赛事的契合度

以「应用创作大赛」类赛事的常见评分维度做对照：

| 评审维度（权重） | 本项目的对应表现 |
|---|---|
| **完成度（通常权重最高）** | 六个脚本、六套模板、双模式全部**实跑通过**，非原型 |
| **创意与场景价值** | 「按行业分模板」+「事实保真闸门」+「反 AI 味 lint」三个点都直击真实痛点，且有调研数据支撑 |
| **使用体验** | 选择成本为零（问行业不问风格）；自然语言改版有明确参数映射；交付即 PDF 可投递 |
| **传播加分** | 「AI 写的简历为什么一眼假」「简历里那个数字是编的」是天然传播话题 |

**有利因素**：求职是刚性高频需求，且同时触达评委与大众受众；
「AI 味」「编造数字」是当下 AI 写作的公共吐槽点，自带共鸣。

**风险因素**：赛道竞争者可能不少（求职类是大热方向），差异化必须讲清楚；
视觉精致度可能不及纯设计向作品。

**判断**：若社媒运营跟上，进入前列概率较高；若仅投稿不运营，大概率落在参与奖区间。
**传播项的投入产出比远高于继续打磨产品。**
