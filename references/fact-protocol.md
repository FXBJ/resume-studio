# 事实保真协议

这是整个 Skill 最重要的一份文档。调研的 7 个开源项目里有 5 个把
「never invent」写进 README——**编造是 AI 简历工具的第一大事故**。
本协议把这条从嘱咐变成流程。

## 三条铁律

1. **输出中的每个公司、学校、职位、日期、数字，必须能在 fact_sheet 里找到来源。**
2. **用户没给的数字，写 `【待补：需要什么】`，绝不填一个看起来合理的值。**
3. **用户说得含糊的，保持含糊。** 「负责多个项目」不要细化成「负责 3 个项目」。

## fact_sheet 结构

```json
{
  "companies": ["公司全称"],
  "schools": ["学校全称"],
  "roles": ["职位名"],
  "dates": ["2023.03", "2024.06"],
  "metrics": [{"value": "120ms", "context": "P99 延迟"}],
  "tools": ["Redis", "Kafka"],
  "vague_claims": ["效果挺好", "多个业务方"]
}
```

`vague_claims` 单独一类——这些是用户原话，保留但要标注为模糊，润色时不许给它们装上数字。

## 什么时候标【待补】

| 情形 | 处理 |
|---|---|
| 用户说「效果挺好的」 | bullet 标 `needs_data`，`data_hint` 写「需要：可核验的指标」 |
| 用户说「大概几千吧」 | 不写进简历，请用户确认后手工填 |
| 用户说「记不清了」 | 标【待补】，不要从上下文推断 |
| 数字来自他人/团队 | 保留但改写归属，如「团队 X 人中我负责 Y」 |
| 用户明确要求编一个 | 拒绝，说明原因，给【待补】 |

## 头像处理

头像走 `meta.photo`，渲染时**自动转 base64 内嵌**，不要写死本地路径：

| 输入 | 行为 |
|---|---|
| `data:image/...;base64,...` | 直接使用 |
| 本地文件路径 | 读文件转 data URI，单文件自包含 |
| 路径不存在 | 输出 NOTE 并跳过头像，**不静默失败** |
| 主题开启头像位但未提供 | 输出 NOTE 提醒 |

为什么必须内嵌：写死本地路径时，HTML 一旦被移动、发给别人、或另存 PDF，图片必然裂图。
data URI 让单文件自包含，打印和分享都不掉图。代价是文件变大（一张 500×700 证件照约 +150KB），
对简历场景完全可接受。

**隐私提醒**：头像是用户本人生物特征信息。只用于用户明确要求放置的简历，
不得写入任何示例、分享物料或测试数据。

## 校验闸门

交付前必跑：

```bash
python3 scripts/check_facts.py --data resume.json --raw raw.json
```

输出 `unsourced=N`。**N > 0 时不交付**，把清单给人看，逐条处理：
能补的让用户补，不能补的改成不含该数字的写法。

白名单数字（不会误报）：`一/二/三…` 中文序号、个位数、`19xx`/`20xx` 年份、
`YYYY.MM` 月份、千分位整数。

## 为什么值得这么严

编造被识破的代价远大于【待补】：

- 面试深挖时圆不上，直接失信
- 背景调查一票否决
- 数字对不上专业常识（如实习生「主导千万级项目」）反而暴露

【待补】是诚实的占位，编造是埋雷。宁可让用户多花五分钟填一个真数。
