# 优化模式 · 已有简历的处理协议

适用：用户手里已有简历文案（md / txt / html / docx / pdf / 直接粘贴），
要润色、结构化重组、专业排版。

## 流程（五步，顺序不要乱）

### 1. 解析

```bash
python3 scripts/parse_resume.py <文件>            # 纯文本
python3 scripts/parse_resume.py <文件> --json     # 带分段
```

解析失败（尤其 PDF）时，不要反复折腾依赖——直接说：「这个 PDF 读不出来，
你把正文文字粘贴给我，一样能处理。」

### 2. 建 fact_sheet（最关键的一步）

把原文里出现的**全部事实**抽成清单，后面每一步都只能引用这个清单里的内容：

- 公司 / 学校 / 机构名
- 职位 / 专业 / 学位
- 时间段
- 数字与单位（含「数千人」这类模糊量词，标注为模糊）
- 工具 / 技术 / 证书名

**原文没有的一律不能加。** 原文含糊的（「负责多个项目」）保持含糊或标【待补】，
不许细化成「负责 3 个项目」。

### 3. 结构化重组

按主题 `module_order` 重排模块。常见修复：

| 原文问题 | 处理 |
|---|---|
| 经历放错位置（把课程设计写在「工作经历」） | 移到 `projects` |
| 「工作经历」里混着社团/志愿 | 拆出去或并入相关条目 |
| 技能只是一串名词 | 按 `category` 分组，JD 关键词前置 |
| 简介是形容词堆砌 | 重写成「身份 + 领域 + 年数 + 最强证据」四要素 |
| 日期格式混乱（2023/3、2023.03、23年3月） | 统一为 `YYYY.MM` |
| bullet 是职责描述（「负责……」） | 改写为「动作 + 对象 + 结果」 |

### 4. 润色（只改形式，不改事实）

允许改的：语序、句式、动词、拆分合并、详略取舍、模块顺序、强调位置。
不允许改的：公司名、职位、时间、数字含义、成果归属。

改写时给用户看 before / after（各 2—3 条即可），让 ta 知道改了什么、为什么。
用户不认可就退回原文写法——**润色是服务，不是覆盖**。

### 5. 质检与交付

```bash
python3 scripts/lint.py --data resume.json
python3 scripts/check_facts.py --data resume.json --raw raw.json
python3 scripts/render.py --data resume.json --out resume.html
```

三者都过，才交付。交付内容与引导模式第 6 步一致。

## 三条特殊情形

**用户只要内容不要排版** → 跳到第 4 步结束，给润色后的 Markdown，不渲染。

**用户说「你看着改，我不懂」** → 仍然要给 before/after 摘要。ta 可能不懂排版，
但必须知道自己的简历被改成了什么样——这是 ta 要拿去投递的东西。

**原文有明显硬伤**（时间断层、错别字、职位与经历不匹配）→ 直接指出来。
指出来是帮忙，藏着是失职。但只提示，不擅自「修复」时间断层这类敏感问题。
